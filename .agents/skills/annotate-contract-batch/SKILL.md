# 契約と内部仕様の注釈

## 範囲を決める

1. リポジトリ直下の `docs/README.md`、`docs/contracts/catalog.json`、依頼に関係する ADR を読む。
2. `git status --short --branch` と `git rev-parse HEAD` を記録する。既存の未コミット変更を上書きしない。
3. 1 バッチを最大 10 単位に区切る。単位をファイル全体、関数、仕様節のどれにするか明示する。
4. 入力がコード・仕様なら `kind=source` とする。「10枚」など画像を示す依頼で画像がない場合は、画像を処理したと記録せず、欠けている入力を報告する。コード調査を画像アノテーションの代わりに数えない。

## 根拠を付ける

1. 実際のソースを読む。各単位にパス、検索できるシンボル、短い原文抜粋、読んだファイルの SHA-256 を記録する。
2. 契約 ID をカタログから選ぶ。確認できた挙動、推論、未解決事項を分ける。テストやモデルが保証する範囲を広げて書かない。
3. 呼び出し元と観測結果を確認する。関数名だけから意味を推測しない。保存グラフの一致から UI・検索順位・クラッシュ回復の一致を推論しない。
4. 検証コマンドを実行した場合は、コマンド・結果・対象版・証跡を保存する。未実行を成功としない。画像、実 GUI、外部ローカルエージェントによるレビューを実施していなければ、その事実を明記する。

## レポートを残す

[記録形式](references/report-format.md) に従い、`docs/reports/YYYY-MM-DD/NNN-topic/` に `manifest.json`、`report.md`、必要最小限の `evidence/` を作る。

- マニフェストの単位 ID と本文の注釈を対応させる。
- `source_revision.base_commit` は調査の基準コミットを表す。未コミットのファイルを読んだ場合は `mode=working-tree` と書く。基準コミットにその内容があると偽らない。
- 追加作業を「対象契約・必要な入力・受入条件・実行する確認」に分け、別のエージェントが始められる粒度にする。
- 将来行うレビューの状態は `pending` とする。実施したレビューだけを証跡付きで `completed` にする。
- 公開済みの過去レポートとハッシュを書き換えない。訂正や再検証は新しいバッチで元のバッチを参照する。

## 検証して引き継ぐ

```sh
pixi run --locked verify-docs
```

必要な実行試験・形式モデルは対象契約に応じて追加する。文書検査の成功を意味的な正しさや網羅性の証明としない。
コミット・プッシュが依頼済みなら、所有する差分だけを確認し、実行結果を記録して通常の手順で公開する。既存の承認を取り直さない。未依頼のマージや強制プッシュは行わない。
最後にバッチのパス、調査件数、検証結果、未解決事項、次のレビュー入力を報告する。
