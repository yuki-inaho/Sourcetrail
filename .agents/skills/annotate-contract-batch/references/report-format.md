# 注釈バッチの記録形式

リポジトリの正式な構成・テンプレートは [docs/reports/README.md](../../../../docs/reports/README.md) と [report.md のテンプレート](../../../../docs/reports/_templates/report.md) を使う。

`manifest.json` の `schema_version` は `1`。次の対応を守る。

| 項目 | 記録 |
| --- | --- |
| `kind` | 現在の手順は `source` のみ |
| `batch_id` / `created_on` | ディレクトリ名と一致させる |
| `source_revision` | 完全な基準コミット SHA、`base-commit` または `working-tree`、その意味の説明 |
| `units` | 1〜10 個。`ANN-001` からの ID、パス、シンボル、SHA-256、短い抜粋、契約 ID、観測、未確定点、次の作業 |
| `finding_type` | `observed` / `inferred` / `unresolved`。読解だけで実行済みとしない |
| `evidence` | コミットする証跡のリポジトリ相対パスと説明 |
| `review` | 外部の次回レビューは `pending`。完了には `evidence_path` が必要 |

`base-commit` は対象内容をそのコミットから読んだ場合にだけ使う。現在の未コミット変更を含む場合は `working-tree` とし、基準コミットは親の出発点であって対象内容そのものではないことを書く。
作業中の最終スナップショットで各ファイルの SHA-256 を計算する。別の担当者が同じファイルを編集している場合は、編集完了を確認してから記録する。

ハッシュは履歴の根拠である。将来の HEAD と一致させるために過去の記録を書き換えない。後続レビューでは該当する履歴・スナップショットを用い、現在のソースとの違いを新しいレポートに書く。

画像を扱う場合は、画像入力・画像の単位・座標やラベル・品質基準・保存方法を先に決め、新しい記録形式を設計する。画像を受け取っていない今回の `source` レポートから画像件数や画像注釈の品質を主張しない。
