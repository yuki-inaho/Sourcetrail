## 前回の未公開実装に関する記録

以下は、2026-10-30の実行記録から確認した内容である。**このブランチで利用できる機能の一覧ではない。**

### GAP-002：入力変更検出

`SourceChange.h` に内容観測の分類を分離し、保存内容が取得できる場合はmtimeの新旧ではなく内容を比較する変更が記録されている。正常な空内容、保存内容の欠落・NULL、ファイル読込失敗、SQL問い合わせ失敗を区別し、索引済み入力の欠落や取得失敗を保守的な再解析へ接続していた。

主な変更対象は `RefreshInfoGenerator::didFileChange`、`TextAccess::tryCreateFromFile`、`SqliteIndexStorage::tryGetStoredFileContentByPath` と、その試験である。保存内容を持たない非索引依存にはmtimeによる弱い互換判定が残っていた。読込中の変更を原子的に固定する機構まで実装したものではない。

### GAP-003：位置規約

`Utf8SourceLocationMap` と `normalizePythonSourceLocations` を追加し、Python由来のUnicodeスカラー位置を保存内容に対応するUTF-8バイト位置へ変換する変更が記録されている。BOM、ゼロ幅、終端列0、最終改行の有無によるスコープ終端を扱っていた。

複数のPythonコマンドは全ワーカー終了後にDB・ソース単位で一度だけ正規化し、不整合な出力を `InvalidOutput` として拒否する構成だった。位置行の更新はID・所属・種類を保持したsavepoint処理、明示的な出力所有衝突は事前拒否としていた。旧Python索引DBを自動移行したものではなく、全体再索引化が必要という制約が残っていた。

### 人工対象から見つかった保存消去の問題

空ファイルへの変更とクリーン再構築の比較で、不要な組み込み型 `int` が残留する差を検出していた。今回の消去で触れた組み込み型だけを回収候補にし、残存する辺・参照元・出現を保護する限定修正が記録されている。一般的な孤立要素回収や、共有出現を持つ辺全体の消去規則を解決したという意味ではない。

## 人工対象の設計・期待値・確認記録

記録上の入口は `tests/input_observation/`、手書き期待値は `fixtures/expected.json` だった。入力操作の前提条件、必要な定義、保存内容、再実行数を個別に確認し、さらに増分更新結果をクリーン再構築の正規化グラフと比較していた。

| 題材 | 記録された確認内容 |
| --- | --- |
| 同一mtime・過去mtimeでの内容変更 | 時刻が進まなくても新しい内容へ更新されること |
| 内容を変えずに時刻だけ変更 | 不要な再解析を避け、意味を保持すること |
| 空ファイル、空からの追加、空への切詰め | 正常な空と取得失敗を混同せず、古い意味要素を残さないこと |
| 保存内容の欠落・NULL | 索引済み入力を未変更扱いしないこと |
| LF／CRLF、最終改行の除去、BOM、Unicode | 保存したテキストと位置が対応すること |
| 同一Python入力の複数実行 | 二重の位置変換や確定を起こさないこと |
| 終了0だがNUL不整合の出力、明示的な所有衝突 | 失敗候補を採用せず既存索引を保持し、修復後の再実行が通ること |
| 観測器の故障入力 | 不正な位置、呼出辺の向き・種類、保存内容等を意図的に壊して、誤った成功を検出すること |

前回の集計記録では、通常観測は入力20・クリーン再構築10・位置8の計38構成、通常CLI実行62回、拒否と修復は2系列・CLI実行10回だった。入力観測のpytestは81実行ケースだった。これらは異なる数え方であり、足し合わせて単一のテスト件数にはしない。
