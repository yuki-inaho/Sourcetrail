# トイプロブレム: 人工的な対象の設計・期待・確認方法

この仕様は、リファクタリングと将来の解析器更新で、どの意味を保つかを小さな実ソースで確認するためのものである。対象は [tests/toy_projects](../../tests/toy_projects/) に保存し、実際の Sourcetrail CLI に索引化させる。設計判断は [ADR-0005](../adr/0005-toy-project-conformance.md)、値処理の再構成は [ADR-0006](../adr/0006-portable-refresh-core.md) を参照する。

## 設計の出発点

トイプロブレムは、単にコンパイル可能な Hello World を追加する作業ではない。既存構成の境界を一つずつ通過し、間違ったときに違いを説明できる最小限の構造を選ぶ。

| 根拠 | 対象へ反映した条件 | 観測する結果 |
| --- | --- | --- |
| ADR-0001: 宣言した観測の同等性 | 完全名、シグネチャ、有向関係、位置、状態を残して比較 | 数値 ID と明示したルートだけを正規化したグラフ |
| ADR-0002: 更新計画の分離 | 無変更、削除、編集、共有依存を異なる段階にする | 更新後の意味が独立した全体更新と一致する |
| ADR-0003: 有限モデルと実装を接続 | 有限の対象を実アプリの入口から処理する | 集合演算の契約だけでは分からない設定・解析・保存の結果 |
| ADR-0004: 対応能力と版 | C++17／Clang 11 と固定 Python 索引器のプロファイルを使う | 宣言した能力の成立と、今回扱わない能力の区別 |
| 内部 C++ と外部 Python の二経路 | 各経路に一つの小規模対象を用意する | 共通の保存観測へ至る異なる実行経路 |
| Python の部分消去不可 | 二つの Source Group の後続側だけから一ファイルを削除する | 先行グループで走査を打ち切らず、必要な全体更新へ進む |

名前・関係・選んだトークン位置の期待は、対象ソースを読んで記述する。保存上の種類や座標規約は、固定したアダプターの仕様と対応させる。初回の DB をそのまま期待値へコピーして、解析器自身を正解の定義にしない。一方、期待値で列挙しない意味も保存するため、全スナップショットの比較を併用する。

## 対象と配置

| ID | 入口 | 意図した小問題 |
| --- | --- | --- |
| `TOY-CXX-001` | [C++ fixture](../../tests/toy_projects/fixtures/cxx/) | 共有ヘッダーにある二つの同名関数を呼び分け、呼び出し元を削除し、名前を変更する |
| `TOY-PYTHON-001` | [Python fixture](../../tests/toy_projects/fixtures/python/) | import と継承を含む複数グループの対象を索引化し、後続グループで削除と編集を行う |

各対象には `initial/` と `updated/` のソース、プロジェクト設定、`expected.json` を置く。削除だけの段階は、初期版から指定ファイルを削除して作る。中間段階を無関係な編集と混ぜず、削除の検出を確かめる。

実行用の compilation database や Python 環境の絶対パスは、隔離した作業ディレクトリに解決する。追跡する fixture に利用者のホームディレクトリや一台だけの絶対パスを埋め込まない。入力を別ルートへコピーし、日本語と空白を含むパスを通す。

### C++ の小問題

`include/api.h` の宣言を複数の翻訳単位から参照する。名前空間 `toy` 内に `answer(int)` と `answer(double)` を置き、`entry()` から両方を呼ぶ。`main()` は `entry()` を呼ぶ。別の翻訳単位 `src/obsolete.cpp` には、削除したときに消える必要がある `obsolete_symbol()` と呼び出しを置く。変更版は両オーバーロードを `replacement` へ改名し、宣言・定義・呼び出しを揃える。

| 仕掛け | 検知したい誤り | 主な契約 |
| --- | --- | --- |
| `int` と `double` のオーバーロード | 表示名だけの正規化で二記号が同一視される | `NAME-001`, `GRAPH-001` |
| 共有ヘッダーと複数翻訳単位 | 依存元の更新漏れ、残る依存先の誤消去 | `REFRESH-001`, `REFRESH-002` |
| 明示した呼び出しと include | 関係の種類・向き・解決先が入れ替わる | `RELATION-001` |
| 名前空間と関数の所属 | 記号は残っても、親からメンバーへの関係だけが消える | `STORAGE-002`, `RELATION-001`, `GRAPH-001` |
| 削除する翻訳単位 | 旧記号・旧関係・旧ファイルが残る | `GRAPH-001`, `REFRESH-001` |
| 関数名と呼び出し側の変更 | 旧名を消さず新名を追加する、参照位置が古いままになる | `NAME-001`, `LOCATION-001` |

ヘッダーの共有保持を全ての場合に保証するものではない。共有・私有の依存、循環、追加・削除の有限入力は、既存の [RefreshPlanTestSuite.cpp](../../src/test/RefreshPlanTestSuite.cpp) と [形式モデル](formal/README.md) でも確認する。E2E では、この対象に対する最終観測を調べる。

### Python の小問題

先行する Source Group に独立した生存ファイル `first/keeper.py` を置き、後続する Source Group にライブラリー `second/library.py`、利用側 `second/main.py`、削除する `second/obsolete.py` を置く。ライブラリーの `Parent` と `helper` を利用側から import し、`Child(Parent)`、`Parent.run(self)`、`helper(41)` の関係を作る。変更版は `helper` を `replacement` へ改名し、import と呼び出しを揃える。

| 仕掛け | 検知したい誤り | 主な契約 |
| --- | --- | --- |
| module の import と呼び出し | 参照先、import 関係、所属する名前が誤る | `NAME-001`, `RELATION-001` |
| 親子クラスとメソッド | 継承と呼び出しを取り違える、同名の所属を失う | `RELATION-001`, `NAME-001` |
| 先行・後続の二グループ | 先行する非該当グループで判定を打ち切る | `SOURCE-GROUP-001` |
| 後続グループから削除だけを行う | 生存ファイルの編集に頼らなければ削除を処理できない | `SOURCE-GROUP-001`, `REFRESH-001` |
| 編集と独立した全体更新 | 外部索引器の結果や後処理が更新経路で食い違う | `GRAPH-001`, `PROCESS-001` |

Python の Source Group は部分消去を許可しないため、更新コマンドでも全体更新へ切り替わり得る。この対象の成功を「変更ファイルだけを解析した」とは表現しない。解析環境には固定版索引器が扱える Python 3.8 を渡し、試験ランナーの Python 3.11 と区別する。[ライフサイクル](../architecture/indexing-lifecycle.md)、[言語互換性](../architecture/language-compatibility.md)

このトイで使う解析深度は `--shallow` を指定しない既定値で、プロファイルは `python-jedi017-full` である。CLI の `--full` は全体更新の指定であり、解析深度の指定とは別である。shallow の確認は既存の [Python E2E](../../tests/python/test_e2e.py) に残し、この対象の期待に混ぜない。

保存上の種類には固定アダプター固有の規約がある。`Parent.run` と `Child.run` は Python のクラス内の関数だが、固定索引器の `beginVisitFuncdef` は `SYMBOL_FUNCTION` を記録する。そのため、このプロファイルの期待値は `NODE_FUNCTION=4096` とする。最初の期待作成時に想定した `NODE_METHOD=8192` は、基準実行と固定版ソースの確認によって訂正した。これは Python の一般的な意味を変更する判断ではなく、既存アダプターの保存表現の明示である。[固定版 indexer.py](https://github.com/CoatiSoftware/SourcetrailPythonIndexer/blob/eba5d0fe5059431bc479b2b36a814b6a9a21bde4/indexer.py#L308-L323)

## 一つの対象で実行する七段階

| 段階 | 入力・操作 | 独立期待の確認 | 同等性の比較先 |
| --- | --- | --- | --- |
| `initial` | 初期版を全体索引化 | 初期の記号、関係、位置、ファイル状態 | 変更前後の同じ段階 |
| `no-op` | ファイルを変えず更新 | 初期の期待を再確認 | `initial` |
| `deleted` | 指定したファイルだけ削除し更新 | 削除済み記号・関係・ファイルが残らない | `deleted-clean` |
| `deleted-clean` | 削除後の入力を別ルートで全体索引化 | 削除後の期待を独立に確認 | `deleted` |
| `updated` | 名前・呼び出し側等を変更し更新 | 新名が存在し、旧名が残らない | `updated-clean` |
| `updated-clean` | 変更後の入力を別ルートで全体索引化 | 変更後の期待を独立に確認 | `updated` |
| `updated-no-op` | 変更後の入力を変えず更新 | 変更後の期待を再確認 | `updated` |

変更検出には既存の mtime 条件がある。編集時刻は、元の mtime と直前の索引化後の時刻の両方より新しくする。この操作は、試験入力を既存の変更検出条件に合わせるものであり、同時刻・過去時刻への書き換えを一般に検出する改善ではない。[INPUT-001 の制約](../architecture/evolution-plan.md#gap-002-更新時刻に依存する変更検出)

## 比較するものとしないもの

`expected.json` は、人が対象を読んで確認できる意味の抜粋である。完全なグラフの代わりではない。記号には種類と保存名の識別を、関係には種類と始点・終点を、選んだ出現箇所にはソース上の範囲を与える。削除・改名した記号やファイルの不在も明記する。

| フィールド | 意味と検査 |
| --- | --- |
| `toy_id`, `language_profile`, `snapshot_profile` | 対象・解析能力・比較規則を識別する |
| `adrs`, `contracts` | 設計理由と守る契約を追跡する |
| `deleted_files` | 削除だけの段階で消す相対パスを明示する |
| `expectations.initial/deleted/updated` | 三つのソース状態に対する独立した期待 |
| `indexed_files` | 索引済みファイルの集合を完全一致させ、`complete` も確認する |
| `symbols` | 種類・完全名・必要なシグネチャで一意に識別する |
| `edges` | 関係の種類と始点・終点を指定し、有向の事実を確認する |
| `occurrences` | 記号、ファイル、位置の種類、開始・終了の行列を指定する |
| `forbidden_names` | 削除・改名後に残ってはならない完全名を指定する |

例えば C++ の同名関数は `name="toy::answer"` だけに縮めず、`postfix="(int)"` と `postfix="(double)"` を分ける。C++ 初期版の索引済みファイルはヘッダーを含め四つ、翻訳単位は三つであり、削除後はそれぞれ三つと二つになる。Python は四つのソースから一つを削除して三つになる。ファイル数と翻訳単位数を混同しない。

全体比較には [semantic_graph.py](../../script/verification/semantic_graph.py) の `schema25-exact-v1` を用いる。数値 ID と宣言したプロジェクトルートを正規化し、完全な名前階層とシグネチャ、位置、出現、曖昧性を含む付加情報、ファイル状態、内容、診断を残す。不明な保存形式や必須構造の欠落を比較成功にしない。

言語間では、共通概念とそれぞれの独立期待を対応させる。C++ と Python の全グラフを等しくする処理はない。対象言語で意味のない機能を無理に足したり、差を消すためにシグネチャや曖昧性を捨てたりしない。

## 実行結果の保存と読み方

通常の回帰確認は次で実行する。ビルド後、二言語の実索引化と、期待値・基準記録を誤って成功扱いしないための試験を行う。全体の `verify` にも含まれる。

```sh
pixi run --locked test-toys
```

このタスクは、現在の実アプリについて独立期待と一回の実行内の同等性を確認する。過去のビルドとの比較は、以下の `--baseline`、または試験用の環境変数 `SOURCETRAIL_TOY_BASELINE` に成功済みの `summary.json` のパスを指定して行う。CI が通ったという事実だけで、指定していない過去版との比較を実施済みとはしない。

[runner.py](../../tests/toy_projects/runner.py) は、指定した出力先に `summary.json` と各言語・段階のスナップショット、プロセスのログを保存する。例:

```sh
pixi run --locked build
pixi run --locked python tests/toy_projects/runner.py --output build/toy-projects/baseline
# 本番コードの変更と再ビルド後に実行する。
pixi run --locked build
pixi run --locked python tests/toy_projects/runner.py --output build/toy-projects/candidate \
  --baseline build/toy-projects/baseline/summary.json
```

基準の実行と変更後の実行で同じアプリを使い回していないことを、実行したバイナリーの SHA-256、ビルド記録、ソースの識別情報で確認する。`--binary-source-revision` は呼び出し側が宣言する情報であり、その文字列だけでバイナリーとの対応を証明しない。未コミット変更を含むビルドでは、基準コミットに加えて変更ファイルのハッシュを記録する。基準の入力・設定・期待値が一致しなければ、単純な同等比較を成立させない。

結果を読む順序は次の通りとする。

1. 宣言した解析器、対象、入力版で実行されたかを確認する。
2. 全段階が存在し、プロセス実行と DB 検査が成功しているかを確認する。
3. 各段階で独立した期待が成立したかを確認する。
4. 無変更／更新対全体更新の比較が成立したかを確認する。
5. リファクタリングの確認では、変更前の全段階と変更後の全段階が一致したかを確認する。
6. 相違がある場合はログとスナップショットを読み、意図した仕様変更か回帰かを記録する。

結果の件数だけで「完全な成功」と判断しない。基準がない、必要な段階が欠けている、別の入力である、期待の検査を実行していない、といった状態を明示的に区別する。実行済みの結果、基準コミット、保管した証跡は [作業レポート一覧](../reports/README.md) から追跡する。

### 最初の基準実行で見つかった既存の差

`993ab43eba5b3055a409a73f686021233a687523` の実アプリに対する実行では、Python の七段階の独立期待と四つの同等性比較が成立した。C++ は削除後の `deleted` だけで独立期待が成立せず、`deleted` と `deleted-clean` の比較も失敗した。他の六段階の独立期待と三つの比較は成立した。[004: 変更前の基準レポート](../reports/2026-10-30/004-toy-project-design-and-baseline/report.md)

差は、残っている名前空間 `toy` から `answer(int)`、`answer(double)`、`entry()` への三つの `EDGE_MEMBER` に限定された。削除後の差分索引はノード十・辺九・位置五十九、同じ入力の全体索引はノード十・辺十二・位置五十九だった。記号と位置が残っていても、所属関係が欠ければ同等ではない。ここで件数だけの比較を採用しているのではなく、厳密な差分から欠けた三つの関係を特定した。

この基準は成功として保存しない。`--record-failures` は期待や同等性の失敗後も全段階の証跡を残すが、終了コードは 1、`summary.json` の状態は `failed` となる。通常の `--baseline` は失敗した基準を拒否する。

これを直す変更では、既存の不具合修正を明示する。受入条件は、欠けた三つの所属関係が戻り、削除後の全体索引と厳密に一致すること、そしてその他の段階に説明のない差を作らないことである。可搬コアへの構造変更の同等性と、この意図した修正を一括して「旧版と完全一致」とは呼ばない。根拠と結果は、基準の失敗を残すレポートと修正後のレポートに分けて記録する。

確認は三つのビルドで区切る。まず元の実装の失敗を保存する。次に保存層の修正だけを加えた実装を実行し、意図した差と独立期待の成立を確認する。その成功結果を比較基準として、可搬コアへのリファクタリングを含む実装の十四段階の観測をすべて厳密比較する。この分け方により、修正のための差を許容したことが、構造変更の説明のない差を隠す理由にならない。

保存層の修正だけを加えた実行では、二言語の十四段階すべての独立期待と八つの同等性比較が成立した。元の実行との差は、C++ の `deleted` に三つの `EDGE_MEMBER` が加わったことだけであり、同じ段階の他の観測項目と、残る十三段階はすべて一致した。この差を、辺の件数だけでなく、追加された辺の種類・両端と削除された辺がないことまで検査している。

続いて、可搬コアと共通の外部コマンド構築を含む変更後の実アプリを実行した。修正だけの成功基準との厳密比較は C++ 七段階、Python 七段階のすべてで一致し、独立期待と実行内の八比較も成功した。[005: 修正とリファクタリングの検証レポート](../reports/2026-10-30/005-portable-core-and-verification/report.md)

| 比較 | 実測結果 | 結果の意味 |
| --- | --- | --- |
| 元実装の独立期待・実行内比較 | C++ の削除後で失敗、Python は成功 | 元から存在した所属辺の欠落を検出した |
| 元実装 → 修正だけの実装 | C++ の `deleted` に所属辺三つを追加。他の十三段階と残る観測は一致 | 意図した修正差を限定した |
| 修正だけの実装 → リファクタリング後 | 十四段階の全観測が厳密一致 | この入力と宣言能力の範囲で構造変更の観測同等性を確認した |

実行中は、過去の成功が残らないよう先に失敗状態の記録を書き、全ての確認が終わってから成功にする。途中の記録を完了結果として読まない。保存済みのレポートは、完了した実行の証跡を選び、現在の作業ディレクトリで再実行した途中結果と区別する。

## 検証器自身の確認

比較器の実装を変更する場合は、正しいスナップショットを読むだけで検証を終えない。意図的に参照先、シグネチャ、位置、段階の識別などを変え、誤った結果が拒否されることを確認する。これは故障の注入先を検証器に限定した試験であり、解析器本体の全ての故障を再現したという意味ではない。

既存の [test_semantic_graph.py](../../tests/contracts/test_semantic_graph.py) は、数値 ID・ルートだけを変えた同等例と、保持すべき意味を変えた非同等例を区別する。トイ用の独立期待と実行記録の検査にも、不正入力を成功扱いしない条件を設ける。

## 新しい解析器や Rust の対象を加える手順

1. 共通概念を選ぶ。定義、呼び出し、依存、位置、削除等のどれを受け持つかを明示する。
2. 対象言語に自然な最小コードを作る。Rust の trait／impl を C++ の継承へ無条件に写す等の変換はしない。
3. エンジン版、edition／規格、依存・features・target 等の入力を固定する。
4. コードから独立した期待を作り、未対応・曖昧・部分結果を完全な成功と区別する。
5. 旧実装が扱える範囲は旧版との比較を行い、新しい能力は独立期待で検証する。
6. 追加した能力と未確認範囲を [言語プロファイル](language-profiles.json)、ADR、レポートへ反映する。
