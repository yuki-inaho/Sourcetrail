# ソフトウェア契約と概念上の同等性

## 何を「同等」とするか

同じ入力ソース `I`、同じビルド・解析設定 `C`、同じ対応能力プロファイル `P` に対して、実装 `A` と `B` が利用者へ提供する観測を比較する。

```text
normalize_P(observe_P(A, I, C)) == normalize_P(observe_P(B, I, C))
```

ここで比較するのは、索引化された記号・関係・位置・診断等の意味である。索引対象プログラムの実行結果が同じかを証明するものではない。検索結果の順位やGUIの操作まで含める場合は、それぞれの観測を追加する必要がある。[ADR-0001](../adr/0001-semantic-observations.md) に設計判断を記す。

言語や解析器の更新では、**両方が対応する能力の共通範囲**を比較する。新しく認識できる構文、より正確な名前解決、修正された誤動作は、旧結果との一致を強制せず、独立した期待値と意図した差を記録する。異なる言語の構文木や全てのノードが同一であることは要求しない。

## 契約の台帳

[catalog.json](catalog.json) を識別子・状態・根拠・検証・説明の対応表とする。

| 状態 | 意味 |
| --- | --- |
| `enforced` | 明記した範囲に実行可能な検査がある。全入力の証明を意味しない |
| `characterized` | 現実装の振る舞いと一部の試験を記録した。横断的な保証は未完成 |
| `planned` | 目標と受入条件。対応実装・実行時の強制は未完成 |

| 契約 | 保存・確認する意味 | 主な検証単位 |
| --- | --- | --- |
| GRAPH-001 | 数値IDから独立した保存グラフ | 比較器の故障検出、実CLIの更新結果と全体再構築の比較 |
| NAME-001 | 修飾名・シグネチャ・オーバーロードの区別 | C++解析器、比較器 |
| RELATION-001 | 辺の種類・方向・曖昧性 | C++／Pythonの実解析、比較器 |
| LOCATION-001 | ソース位置・種別・記号との結び付き | 解析器、永続DB |
| REFRESH-001 | 更新対象の集合計画 | C++独立オラクル、TLA+詳細化 |
| REFRESH-002 | 未変更ソースが使う共有依存の保護 | C++、TLA+、故障モデル |
| REFRESH-003 | 未完了ファイルと依存ソースの再試行 | DBを使うC++試験、CLI |
| SOURCE-GROUP-001 | 所属判定と明示した除外集合 | 空／単一／複数グループのC++試験 |
| INPUT-001 | 更新時刻と内容の分類条件 | 既存の入力分類試験、制約の記述 |
| STORAGE-001 | スキーマ・保存・参照整合性 | SQLite試験、比較器の破損入力拒否 |
| STORAGE-002 | 生存する親・子の階層メンバー辺を保持 | 削除専用C++トイ、6ケースのSQLite契約試験 |
| DIAGNOSTIC-001 | 診断、位置、部分結果 | 構文エラー・修復の実索引化 |

| COMMAND-001 | 順序付き変数展開、引数境界、生テンプレート、実行時DB差し替え | 標準C++単独試験、既存コマンド型の契約試験、Python実E2E |

| PORTABILITY-001 | 言語・OSアダプターから独立した値契約 | Qt等なしのビルド、共通値入力に対するC++／Rust／独立オラクルの照合 |
| QUERY-001 | 検索・ナビゲーション・キャッシュ | 既存検索試験、今後の問い合わせ適合試験 |
| LANGUAGE-001 | 版と対応能力の宣言 | [能力プロファイル](language-profiles.json)、実行時の交渉は計画段階 |
| PUBLICATION-001 | 索引の採用と障害復旧 | 計画段階。現状の削除後renameは原子性を保証しない |
| VERIFICATION-001 | 検証器の誤成功防止 | TLC終了状態・反例・ハッシュの検査 |

## 実行可能なグラフ比較

[semantic_graph.py](../../script/verification/semantic_graph.py) の `schema25-exact-v1` は、完了した索引DBを読取専用の一つのトランザクションで読み、次を比較する。

| 残す観測 | 正規化・除外する表現 |
| --- | --- |
| ノード種別、名前の階層と区切り、署名の前置部・後置部 | 数値ノードID、行の保存順 |
| 記号の定義種別、辺種別と向き | 数値の辺ID・位置ID |
| ファイルの言語、indexed／complete、行数、保存内容のSHA-256 | `modification_time` |
| 出現と全ての位置種別・開始／終了座標 | 指定したプロジェクトルートのパス接頭辞 |
| ローカル記号、アクセス属性、曖昧性を含む要素成分 | 作業用メタデータ（設定・時刻等。schema版は検査する） |
| 診断本文、致命性、索引状態、翻訳単位、位置 | 診断等に現れる明確なプロジェクトルートの接頭辞 |

外部SDKや環境の絶対パスは保存する。ソース本文内の文字列は正規化せず、内容のハッシュを保持する。名前は表示用の短縮名へ変換しない。ローカル記号の生成名や診断文面も保持するため、解析器の更新で差が出たときは無視規則を足す前に意味を確認する。

`element` の未参照の採番専用行も観測から除く。現実装の `addSourceLocations` は基底要素を採番する一方、位置には別のID列を使用するためである。型を持つ要素の基底行がない場合や、出現・成分が型のない要素を参照する場合は拒否する。

重複行の多重度は保持する。解釈が曖昧になる同一キーの重複、参照切れ、想定外の表・列・schema版、読み取れない名前は比較不能として拒否する。空の索引同士が一致しても「必要な記号が揃った」ことにはならないため、E2E試験は期待する記号・辺・診断も検査する。

```sh
# 同一入力・設定の変更前と変更後の索引を比較する。
pixi run python script/verification/semantic_graph.py compare \
  /path/to/before/project.srctrldb /path/to/after/project.srctrldb \
  --before-root /path/to/before --after-root /path/to/after

# レビュー用の正規化JSONを保存する。
pixi run python script/verification/semantic_graph.py export \
  /path/to/project.srctrldb --root /path/to/project \
  --output build/verification/project.graph.json
```

比較の終了コードは **0: 同等、1: 意味の差、2: 入力または比較条件が不正**。同等性を判断するときは、入力のハッシュ、設定、解析器版、能力プロファイルもレポートに残す。DBはそれら全てを自動的に証明する証拠ではない。

### 更新結果と全体再構築

C++の実プロジェクトでは、共有ヘッダーとオーバーロードを持つ入力を索引化し、変更・削除後の更新結果を同じ最終入力の全体再構築と比較する。Pythonでも、変更・削除後の索引を同じ観測で比較する。Pythonは構成によって全体再索引化へ昇格するため、この成功から部分更新の実行を推論しない。

旧版と新版の比較を行う場合は、同じ入力と設定を二つの環境へ配置して各索引を保存し、明示したプロファイルで比較する。今回の更新計画抽出は、既存試験に加え、独立した閉包アルゴリズムによる32,768入力の検査で支える。全アプリケーションに対する旧版／新版の形式証明ではない。

## TLA+と実装の対応

[トイ対象](toy-problems.md) は、手書きの必要な事実と索引全体の厳密比較を併用する。
C++の削除専用入力は旧版の所属辺欠落を発見したため、旧版、修正のみの版、構造変更後の版を分けて記録する。
修正後の基準からのリファクタリングは全14段階の一致で検査する。失敗した旧基準を成功した比較基準として読み込むことは拒否する。

更新コアの移植は [ADR-0006](../adr/0006-portable-refresh-core.md) の値境界を使う。
`pixi run -e portability --locked verify-portability` は標準C++の独立ビルドと、Rust参照移植・独立した期待値との照合を行う。
これはRustソースの索引化や、本体全体のRustへの置換を実装したという意味ではない。

[形式仕様](formal/README.md) の更新計画モデルは、変更集合、未変更集合、ソース集合、include／import関係を入力とし、消去集合・索引集合を観測する。段階的な計算が抽象契約の一回の戻り値と対応することを、有限状態で検査する。

[外部実行結果の契約](external-indexing.md)は、コマンドの開始と結果確定、失敗の集約、候補の破棄、終了通知を別の検証単位にする。`ExternalIndexing` モデルの採用判断と、実CLIで観測する終了コード・既存DBの保持を対応させる。外部タスクがスケジューラー上で完了したこと、プロセスが終了コード0を返したこと、意味的に正しい索引を持つことを区別する。

検証単位を混同しない。

1. **仕様の検査:** 集合計画の不変条件と詳細化をTLCで探索する。
2. **実装の検査:** 同じ契約をC++の本番関数へ独立した期待値で適用する。
3. **接続の検査:** 実CLIからDBまで実行し、定義・参照・更新結果を確認する。
4. **根拠の追跡:** 台帳・ADR・ソース注釈・レポートを対応づける。

形式モデルの成功だけで、ファイルの変化検出、並行処理、索引器の正しさ、公開の原子性、終了の必然性を保証しない。モデルが置いた前提は、実装側の別の契約で確かめる必要がある。

## 拡張とレビュー

変更する前に、影響する契約IDと能力プロファイルを選ぶ。対象が既存の観測で足りなければ、観測と反例を追加してから内部構成を変更する。意図した不具合修正は、旧結果との差を記録する。`SOURCE-GROUP-001`、`STORAGE-002`、`EXECUTION-001` はその例である。

次の改善範囲と受入条件は [GAP一覧](../architecture/evolution-plan.md)、少数単位での注釈・レビュー・追加作業の記録方法は [レポート運用](../reports/README.md) を参照する。
