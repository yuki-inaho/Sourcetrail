# 外部索引器の実行結果と候補索引の採用

契約ID: **EXECUTION-001**。設計判断: [ADR-0007](../adr/0007-external-indexer-outcomes.md)。適用対象はPython／Customが使う外部コマンド実行経路である。更新計画、構文診断、保存グラフ、DB公開の障害耐性にはそれぞれ別の契約がある。

## 三つの結果を分ける

| 結果 | 観測するもの | この契約との関係 |
| --- | --- | --- |
| スケジューラーの完了 | タスク列が終了処理まで進んだか | 外部コマンドに失敗があっても、後始末と結果通知を実行する |
| 外部プロセスの結果 | 実行エラー、終了コード | 本契約の成功・失敗分類と集約の入力 |
| 解析・保存した意味 | 記号、関係、位置、診断、完全性 | `GRAPH-001`、`DIAGNOSTIC-001`等の別の観測が必要 |

`STATE_SUCCESS` はスケジューラー上の完了であり、索引化全体の成功という値には使わない。外部コマンドが正常終了しても、そのDBが必要な内容を持つことを自動的には示さない。

## 入力と分類

[classifyExternalProcess](../../src/lib_core/ExternalIndexerOutcome.h) は、既存の `utility::ProcessOutput` から実行エラーの有無と整数の終了コードだけを受け取る。

| 実行エラー | 終了コード | 分類 | 期待する件数処理 |
| --- | --- | --- | --- |
| あり | 任意 | `TransportError` | 結果確定数と失敗数を増やす |
| なし | 0以外 | `NonzeroExit` | 結果確定数と失敗数を増やす |
| なし | 0 | `Succeeded` | 結果確定数と成功数を増やす |

実行エラーがあれば終了コードより優先する。stderrへ文字を書いただけでは実行エラーにしない。現行の [executeProcess](../../src/lib_gui/utility/utilityApp.cpp) はstdoutとstderrを結合して `output` へ収集し、Boost.Processで捕捉したエラーを `error` へ入れる。

終了コード0でDBへ何も書かないコマンドも、プロセスの分類は `Succeeded` である。既存Custom拡張は出力能力の交渉を行っておらず、本変更で「最低一つのノード」などの新しい出力要件を暗黙に追加しない。必要な内容の検査は、明示した能力と期待値へ接続する後続作業になる。

## 一回の実行の集約

コアの `ExternalIndexerOutcome` に、開始数 `attempted`、結果確定数 `settled`、成功数 `succeeded`、失敗数 `failed` を保持する。コマンドの開始を記録してから、返った結果を一度だけ確定する。実アダプターでは [ExternalIndexerRunState](../../src/lib/data/indexer/ExternalIndexerRunState.h) が同期を担当する。

正しい呼び出し列の不変条件は次の通り。

```text
settled = succeeded + failed
settled <= attempted
failed は同じ実行中に減少しない
hasFailure = (failed > 0)
```

並列実行では結果確定の順序が開始順と異なり得る。後の成功や、別のワーカーの成功で、既に記録した失敗を消してはならない。新しい索引化・再試行には新しい実行状態を使う。

ここでの集約の入力は、開始され、プロセスヘルパーから結果が返ったコマンドである。取消による未開始コマンドや、ヘルパーが返らない実行の完了性を、この式から保証しない。

## 件数・採用・終了通知

`TaskExecuteCustomCommands` は成功した外部コマンドだけを `indexed_source_file_count` に加える。実行失敗は構文診断のDB行へ偽装せず、外部実行の結果として終了処理へ渡す。成功数が実際に保存された定義数や完全なソース数と同じだとは扱わない。

| 実行状態 | 候補索引と後処理 | 終了結果 |
| --- | --- | --- |
| 外部実行失敗なし | 従来のPython後処理・診断表示・DB採用判断へ進む | 従来の成功経路を維持 |
| 外部実行失敗あり | Python後処理を省き、候補DBを破棄。GUIの採用選択で失敗を上書きしない | 破棄と更新段階の解除後に失敗を通知。CLIは非ゼロ終了 |

既存の採用済みDBがあれば、失敗した候補で置き換えない。採用済み索引がない初回索引化でも、失敗候補を採用しない。プロジェクト初期化による未採用の空DBが残る場合があるため、この条件をメインDBファイルの不存在とは定義しない。タスク列の後始末を飛ばさず、次の再試行へ進める状態で終わることを観測する。

実装上の入口は [TaskFinishParsing](../../src/lib/data/TaskFinishParsing.cpp)、[Project](../../src/lib/project/Project.cpp)、[MessageIndexingFinished](../../src/lib/utility/messaging/type/indexing/MessageIndexingFinished.h)、[Application](../../src/lib/app/Application.cpp)、[MessageQuitApplication](../../src/lib/utility/messaging/type/MessageQuitApplication.h) である。成功側の既定値を保ち、既存の成功通知の呼び出し元へ一律に新しい失敗条件を加えない。

### 採用していないDBの識別

人工対象の [read_index_observation](../../tests/external_indexer/harness.py) は、ファイルの存在だけで採用済み索引と判断せず、次の状態を区別する。

| 観測状態 | 判定 | 意味スナップショット |
| --- | --- | --- |
| `absent` | DBファイルが存在しない | なし |
| `uninitialized-empty` | 初期化時の既知の表・列名と完全一致し、metaを含む全表が0行。既知のoccurrence主キー索引だけがあり、SQLiteの整合性検査を通る | なし |
| `schema-25` | 変更していない厳密な意味比較器で、有効なschema-25索引として読める | あり |

初回失敗の受入条件は、CLIの失敗・成功数・一時DBの除去に加え、採用済みの `schema-25` 観測がないことである。未初期化の例外を空の意味グラフとして正規化しない。この例外は、非空の未版付けDB、未知の表・列・索引を持つ初期化DB、破損ファイルを許容しない。既存の採用済み索引を保つ試験では、実C++解析器で作った基準スナップショットとの厳密一致を要求するため、`absent` や `uninitialized-empty` で保存の成功を代用できない。

## 人工対象の設計と受入条件

[tests/external_indexer](../../tests/external_indexer/)は、実解析器の構文処理へ依存せず、実アプリのプロセス境界を小さく再現する人工対象である。既存のC++／Pythonトイが「解析された意味」を検査するのに対し、ここでは外部呼び出しと結果の採用を検査する。スクリプトの直接呼び出しだけで合格にせず、Custom Source Groupを設定した実CLIから起動する。

| シナリオ | 独立した期待 |
| --- | --- |
| 存在しない実行ファイル | 失敗を成功数へ数えず、候補を採用せず、CLIが失敗する |
| 非ゼロ終了 | 終了コードを失敗へ分類し、同じ採用・通知規則に従う |
| stderr付きの終了コード0 | プロセス成功を維持し、警告出力を失敗へ読み替えない |
| 書き込みなしの終了コード0 | プロセス成功という互換性を記録し、意味的完全性を主張しない |
| 成功と失敗を含む複数コマンド | 後続の成功で失敗を消さず、成功した分だけを成功数へ数える |
| 採用済みDBがある状態で失敗 | 変更前後の採用済みDBの観測が一致する |
| 失敗後の正常な再試行 | 一回前の失敗を引き継がず、終了処理が次の実行を妨げない |

成功したC++／Pythonの固定入力には、既存の [schema25-exact-v1](README.md#実行可能なグラフ比較) と [トイ対象](toy-problems.md)を使う。失敗の意味を直す差と、成功した索引結果の一致を別々に記録する。実測の対象版、コマンド、結果、未確認事項は [レポート](../reports/README.md)を参照する。

## 形式検査と実装の対応

[ExternalIndexing.tla](formal/ExternalIndexing.tla) は、2〜3個のコマンドの開始・結果確定・候補の処分・終了通知という有限の状態遷移を扱う。各コマンドの返る結果を入力として与え、異なる確定順で集約と採用の契約を検査する。成功した候補は採用または破棄を選べる一方、失敗した候補は破棄する。GUIで正常な候補を破棄してもプロセスの実行失敗へ変換しない。共有状態を更新するC++実装の同期、メッセージ経路、ファイル処分は、実装試験と実CLIの観測で対応を確認する。[形式仕様の実行手順](formal/README.md)

モデル内の一遷移で採用済みDBを保持しても、実ファイルシステムの原子性やクラッシュ回復は証明されない。中断した子プロセスの寿命、任意のスレッドスケジュール、索引器の意味的正しさもモデルの外である。

## 残る条件

- **出力の意味と版:** 空出力、破損DB、未対応保存版、未対応構文を検査する能力交渉と結果検査は今後の対象。
- **タイムアウト・取消:** 現行 `executeProcess` では `ios.run()` によるパイプ処理がタイムアウト待ちより先にある。ソース上の順序を記録した段階であり、今回の試験で実効タイムアウトや特定のハングを確認したという記述ではない。
- **公開中の障害:** 本契約は失敗が判明した候補を採用しない。削除後renameの障害耐性は `PUBLICATION-001`／`GAP-001` に残る。
- **入力の変化:** mtimeが同じ、または逆行した場合の内容変更検出は `INPUT-001`／`GAP-002` に残る。
- **適用範囲:** 内部C++／Javaワーカー、全OS、新しいPython／C++構文、Rustソース解析の対応はこの外部実行結果契約から推論しない。

後続の受入条件は [GAP-005](../architecture/evolution-plan.md#gap-005-外部索引器の失敗と終了状態) で追跡する。
