# ADR-0004: 言語名とは独立した対応能力と版を管理する

- 状態: 方針を採用。新アダプター API／Rust 実装は提案段階
- 日付: 2026-10-30
- 関連契約: `LANGUAGE-001`, `PROCESS-001`, `NAME-001`
- 関連仕様: [言語互換性と拡張点](../architecture/language-compatibility.md)

## 背景

現行は C++／Java の内部解析と、Python／Custom の外部コマンドで経路が異なる。ビルド時の言語フラグ、Source Group の型、設定保存、ワーカー、UI に言語固有の分岐がある。言語名を増やすだけでは、新しい対象を同等の探索操作へ接続できない。

また、試験を実行する Python の版と、旧 Python 索引器が調べる環境の版は別である。C++ のビルド用コンパイラーと、対象ソースを解析する Clang の版も別である。これらを一つの「対応バージョン」として示すと、実際の能力より広く見せてしまう。

## 決定

言語アダプターごとに、識別子、エンジン版、対象言語の版／edition、プロトコル版、保存形式、対応能力を明示する。機能を定義・参照・呼び出し・依存・診断・位置・更新等の単位に分け、宣言した能力に適合試験を対応させる。

共通契約は、利用者の探索操作に必要な意味を定義する。言語固有の意味を失う無条件の写像は行わない。Rust の trait／impl、マクロ展開、cfg、crate の同一性などは追加仕様として決める。

旧版で対応する入力は、その版を固定した基準結果と比較する。新しい構文は独立した期待値と比較する。未対応入力、未解決参照、部分結果、起動失敗を、完全な成功と区別できるようにする。

基準環境は固定したまま、更新候補の環境を並行して検査できる構成とする。現在の pixi の試験ランナー環境と `python-parser` 環境の分離を、対象言語の版管理と混同しない。

## 提案する責務分割

| 責務 | 役割 |
| --- | --- |
| プロジェクト文脈の取得 | compilation database、Python 環境、Cargo workspace 等を読み、再現可能な入力を作る |
| 意味解析 | 固定したエンジンが記号・関係・位置・診断を抽出する |
| 共通表現への写像 | 言語固有の同一性、関係、確信度、座標を、宣言した契約へ写す |
| 実行の管理 | 引数、cwd、環境、失敗、取消、版の整合を管理する |
| 更新の計画 | アダプターが宣言した依存・部分更新能力から更新対象を決める |
| 保存・問い合わせ | 言語共通の探索可能な観測を提供する |

この表の責務を実装へ分離する作業は段階的に行う。最初から新しいプラグイン ABI を安定版として公開しない。

## 代替案

| 案 | 問題 |
| --- | --- |
| pixi の Python／LLVM の版だけを上げる | アダプター API、構文の意味、位置、後処理、配布の互換性を確認できない |
| 全ての言語を同じ型・関係に強制する | 言語固有の意味や曖昧性が失われる |
| Rust を Custom コマンドで動かせば完了とする | 初期試作には使えるが、設定・失敗・更新・検索の同等性が未確認 |
| 最初から全アプリを Rust 等へ書き換える | 既存の探索上の意味を比較する単位が大き過ぎる |

## 検証と未達成事項

各アダプターで宣言した能力の小さな例を実索引化し、DB と問い合わせの観測を確認する。変更、削除、無変更の再実行、診断修復、Unicode の位置、同名記号、曖昧な参照も確認する。

本変更は、将来の対応能力と受入条件を整理する。新しい Python／C++ 構文の一般対応や Rust 索引器を実装したとは扱わない。具体的なバックエンド選定、公開プロトコル、版交渉、構文別の期待は後続の変更で確定する。[GAP-006／GAP-007／GAP-009](../architecture/evolution-plan.md)
