# ADR-0007: 外部索引器の実行結果を集約し、失敗した候補索引を採用しない

- 状態: 採用。起動・実行エラーと非ゼロ終了の範囲
- 日付: 2026-10-30（Asia/Tokyo）
- 関連判断: [ADR-0004](0004-language-capabilities.md)、[ADR-0005](0005-toy-project-conformance.md)、[ADR-0006](0006-portable-refresh-core.md)
- 関連契約: `EXECUTION-001`, `COMMAND-001`, `DIAGNOSTIC-001`, `GRAPH-001`, `VERIFICATION-001`
- 詳細: [外部索引器の実行結果と採用の契約](../contracts/external-indexing.md)

## 背景

[ADR-0006](0006-portable-refresh-core.md)で外部コマンドの構築を共通化したが、実行結果の扱いは [TaskExecuteCustomCommands](../../src/lib/data/indexer/TaskExecuteCustomCommands.cpp) に残っていた。変更前は起動エラーや非ゼロ終了をログへ記録した後も `indexed_source_file_count` を増やし、実行タスクは `STATE_SUCCESS` を返した。後続の終了処理には、その実行で外部コマンドが失敗したという情報が渡らなかった。

この状態で新しい解析器を追加すると、配置・設定・版の不整合による実行失敗と、解析が終わった結果を区別しにくい。[ADR-0004](0004-language-capabilities.md)の実行管理を、現在のPython／Custom経路で強制できる小さい境界から実装する。

また、タスクの `STATE_FAILURE` を返すだけでは解決しない。[TaskGroupSequence](../../src/lib/utility/scheduling/TaskGroupSequence.cpp) は後続のタスクを実行しなくなるため、一時DBの処分、更新段階の解除、完了メッセージまで飛ばしてしまう。スケジューラーが処理を終えたことと、索引器の実行が成功したことは別の値で扱う必要がある。

## 決定

### 1. プロセス結果を値として分類する

[ExternalIndexerOutcome](../../src/lib_core/ExternalIndexerOutcome.h) を標準C++だけの値処理とし、`classifyExternalProcess` は既存のプロセスヘルパーから受け取った実行エラーの有無と終了コードを分類する。

| 条件 | 結果 | 成功数への加算 |
| --- | --- | --- |
| 実行エラーあり | `TransportError` | なし |
| 実行エラーなし、終了コードが非ゼロ | `NonzeroExit` | なし |
| 実行エラーなし、終了コードが0 | `Succeeded` | あり |

`utility::ProcessOutput.error` はプロセスの起動・実行で捕捉したエラーである。標準エラー出力は標準出力と共に `output` へ収集されるため、警告をstderrへ出しただけの終了コード0を失敗に変えない。[utilityApp.cpp](../../src/lib_gui/utility/utilityApp.cpp)

出力のないコマンドも検査対象にするため、ログ収集では空の読込コールバックで文字列末尾へアクセスしないようにする。無出力と改行終端の実プロセス試験を置き、表示の有無で実行結果が変わらないことを確認する。[UtilityTestSuite.cpp](../../src/test/UtilityTestSuite.cpp)

ここでの `Succeeded` は、プロセス呼び出しが成功したという意味である。DBに書き込みがない終了コード0も、この分類では成功する。必要な記号、診断、保存スキーマ、完全性の判定には別の解析結果契約が必要になる。

### 2. 実行単位で失敗を保持する

コアの `ExternalIndexerOutcome` は開始した数、結果が確定した数、成功数、失敗数を分ける。並列呼び出し側は [ExternalIndexerRunState](../../src/lib/data/indexer/ExternalIndexerRunState.h) で更新とスナップショット取得を同期する。一度記録した失敗は、後の成功で消さない。

状態は一回の `Project::buildIndex` の処理へ渡す。別プロジェクトや次の再試行へ失敗を引き継ぐグローバル状態にはしない。終了コードの分類、カウンターの集約、GUI・DB・プロセスの操作を同じ責務へ集めない。

### 3. 後始末を終えてから結果を通知する

`TaskExecuteCustomCommands` はコマンドの結果を記録し、外部コマンドが成功したときだけ既存の索引済み件数へ加算する。失敗を含む実行ではPython後処理を行わない。タスク列は終了処理まで進み、`TaskFinishParsing` は失敗した候補DBを破棄する方針を選ぶ。

この破棄方針はGUIの採用選択でも上書きしない。既存の採用済み索引がある場合はそれを保持し、初回索引化で失敗した場合は候補を採用しない。破棄と更新段階の解除を終えた後に `MessageIndexingFinished` で実行結果を伝える。ヘッドレス実行は `MessageQuitApplication` を通して非ゼロの終了コードを返す。

初回失敗でも、プロジェクト初期化で作られた未採用の空DBが残る場合がある。「候補を採用しない」はメインDBファイルの不存在を要求するものではない。人工対象は未初期化の既知の空構造と採用済みschema-25索引を区別し、意味比較器の検査は弱めない。[未採用DBの識別](../contracts/external-indexing.md#採用していないdbの識別)

失敗のない実行は、従来の診断表示、DB採用方針、Python後処理、CLI終了を保つ。構文診断が存在することと外部プロセスが失敗したことを同一視しない。内部C++／Javaワーカーの終了状態は、この外部コマンド用の契約へ暗黙に含めない。

## 意図した振る舞い変更

起動できなかったコマンドや非ゼロで終了したコマンドを、索引済み成功数へ数えない。該当する実行の候補索引は採用せず、CLIは失敗を返す。この差は、既存の不適切な成功扱いを修正する変更として記録する。

成功したC++／Python対象の保存観測には従来の比較プロファイルを使い、説明のない差がないことを確認する。失敗経路の修正を通すために、既存の正常系スナップショットや比較条件を弱めない。

## 人工対象と検証

[人工の外部索引器](../../tests/external_indexer/)は、成功、stderr付き成功、書き込みなしの成功、非ゼロ終了、起動不可を分けて再現する。実アプリのCustom Source Group経由で実行し、終了コード、件数、候補DBの処分、既存索引の保持、再試行を観測する。正常系のC++／Pythonトイは、変更前後の保存グラフを比較するために継続する。

検証は、値分類と集約のC++試験、実CLIの障害対象、[ExternalIndexingの有限モデル](../contracts/formal/ExternalIndexing.tla)に分ける。有限モデルでは結果確定の順序を変え、失敗を成功へ戻さないこと、失敗した候補を採用しないこと、終了処理との対応を確認する。指定した規則を壊した変異モデルも反例を検出できることを要求する。実行した件数・状態数・前後差は [作業レポート](../reports/README.md)へ保存する。

## 代替案

| 案 | 採用しない理由 |
| --- | --- |
| ログだけを詳しくする | 終了処理・CLI・DB採用の判断に失敗が届かない |
| 外部タスクから直ちに `STATE_FAILURE` を返す | タスク列の後始末と完了通知を通らなくなる |
| stderrに出力があれば失敗とする | 正常な警告・進捗表示まで失敗へ変えてしまう |
| 終了コード0を完全な索引の証明とする | 空出力や不適切な内容を検査できない |
| 最初に汎用プラグインABIや全能力交渉を作る | 今回必要な実行結果を渡す境界より責務が広く、未実装の解析器仕様を固定してしまう |

## 未達成事項

`GAP-005` はこの実行失敗の範囲で改善する。タイムアウト、取消、子孫プロセスの回収、異常なDB出力、エンジン版の交渉、全OSの実行は引き続き別の受入条件である。現行ヘルパーではパイプ読込の `ios.run()` がタイムアウト待ちより先にある。この呼び出し順はソースで確認したが、今回の分類追加だけで実効的なタイムアウトや特定のハングを実証したとはしない。

候補の採用前に判明した失敗の扱いと、採用中のクラッシュ耐性は分ける。既存の削除後renameを原子的な置換へ変えていないため、`PUBLICATION-001`／`GAP-001` は未完了のままとする。更新時刻による検出の制約 `GAP-002`、座標規約 `GAP-003`、新Python／C++構文とRust索引器も次の作業として残す。[改善順序と未解決事項](../architecture/evolution-plan.md)
