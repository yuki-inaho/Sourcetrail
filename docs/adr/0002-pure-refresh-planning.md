# ADR-0002: 更新計画の集合演算を独立させる

- 状態: 採用
- 日付: 2026-10-30
- 関連契約: `REFRESH-001`, `REFRESH-002`, `REFRESH-003`, `SOURCE-GROUP-001`
- 関連仕様: [索引化ライフサイクル](../architecture/indexing-lifecycle.md)

## 背景

`RefreshInfoGenerator::getRefreshInfoForUpdatedFiles` は、ファイルの分類、依存関係、共有ヘッダーの保持、索引化対象の決定、索引対象／非対象の分割を一つの処理に持っていた。ファイルシステムと DB の準備なしに、集合として何が守られるべきかを調べにくかった。

特に、変更したソースだけが参照する依存先は消去し直す一方、変更されない別ソースが使う共有依存先は維持する必要がある。変更・削除・追加を一つずつ例示するだけでは、依存の組み合わせの取り違えを発見しにくい。

## 決定

[RefreshPlan::forUpdatedFiles](../../src/lib/project/RefreshPlan.h) を抽出し、全ソース、変更のない索引済みファイル、変更ファイル、および `referenced`／`referencing` の問い合わせを入力にする。出力は消去集合と索引化集合とする。

本体は集合演算に限定する。問い合わせは、同一の固定スナップショットに対する決定的で読み取り専用の関数であることを前提とする。実運用のコールバックは `PersistentStorage` を読むため、実行全体を無条件に I/O のない関数と呼ばない。

`RefreshInfoGenerator` には、ファイルの存在・mtime・内容による分類、Source Group の有効状態、索引対象／非対象の分割、不完全ファイルの追加を残す。`Project` の実行・公開も移動しない。

依存関係は、現行の include 閉包と import 閉包をそれぞれ求めて和集合にする仕様を保持する。両者を混ぜた閉包へ変更する場合は、別の意味変更として扱う。

`FilePath` の集合は順序比較を使う。`FilePath::operator==` は存在するパスのファイルシステム上の同値性を調べるため、純粋な集合の比較に無造作に持ち込まない。パスの正規化は呼び出し側の責務とする。[FilePath.cpp](../../src/lib/utility/file/FilePath.cpp)

## 別の変更として扱う包含判定の修正

Source Group の補集合を返す API の曖昧な名前と、通常の包含を期待する呼び出しを整理する変更は、更新計画の等価な抽出とは分ける。本変更では `containsSourceFilePath` の誤った包含判定を `SOURCE-GROUP-001` の振る舞い修正として直し、再現例・期待値を持つ。補集合は `getSourceFilePathsExcept` と明示し、旧 API は転送用の別名として残す。既存挙動と異なる部分を等価性の証拠に混ぜない。

`Project::buildIndex` で部分消去不可のグループを調べる際は、現在のソース集合への包含ではなく、設定したソースパスと除外条件による所属を使う。削除済みファイルも `filterToContainedFilePaths` で所属を判定し、該当しないグループの後も走査を続ける。該当グループがあれば全体更新へ切り替え、shallow 指定と GUI の確認／取消は保持する。削除だけの更新と、後続グループに所属する削除を明示した回帰試験を置く。[Project.cpp](../../src/lib/project/Project.cpp)、[SourceGroupContractTestSuite.cpp](../../src/test/SourceGroupContractTestSuite.cpp)、[Python E2E](../../tests/python/test_e2e.py)

この修正に伴う試験の時刻設定も区別する。固定版の外部 Python 索引器は記録時の時刻を保存するため、内容変更試験の mtime は保存時刻より新しくする。全体更新への誤った切り替えによって時刻条件を満たさない試験が偶然通ることを避ける。この前提を正すことと、mtime 依存の変更検出自体を再設計することは別の作業である。[時刻の内部仕様](../architecture/indexing-lifecycle.md#純粋計画の外に残る判定)

## 代替案

| 案 | 評価 |
| --- | --- |
| 既存の大きな関数をそのまま試験する | 実アプリでの確認は続けるが、依存関係の有限列挙に不要な I/O が混ざる |
| DB の全依存グラフを新しい型へ読み直す | 将来案にはなるが、今回の抽出で性能と依存取得仕様を同時変更する必要がない |
| 更新の状態機械・DB 公開も同時に全面改修する | 検証単位が大きくなり、意味の差の原因を特定しにくい |
| ファイル名文字列だけの新型へ全面置換する | パスの同一性規約を別途定めてから扱うべき変更 |

## 検証と限界

集合結果の C++ 試験、既存の `RefreshInfoGenerator` 試験、実アプリの差分更新試験を維持し、TLA+ の有限モデルを追加する。形式モデルとの関係は [ADR-0003](0003-bounded-formal-verification.md) で定める。

本判断は、mtime が全変更を検知すること、問い合わせスナップショットが並行変更から守られること、消去後の解析や公開が成功することを保証しない。これらは独立した契約と検証単位を必要とする。

## 後続の具体化

[ADR-0006](0006-portable-refresh-core.md) では、この入力・出力と問い合わせ順を保持したまま、集合演算を `src/lib_core/RefreshPlanner.h` の二段階の値処理へ移す。`RefreshPlan::forUpdatedFiles` は既存の `FilePath` とストレージ問い合わせのアダプターとして残る。本 ADR の計画式・パス同一性・固定スナップショットの前提を置き換える判断ではない。
