# ADR-0003: 有限モデルと実装の適合試験を組み合わせる

- 状態: 採用
- 日付: 2026-10-30
- 関連契約: `REFRESH-001`, `REFRESH-002`
- モデルと実行手順: [contracts/formal/README.md](../contracts/formal/README.md)

## 背景

回帰試験と E2E は具体的な入力から出力を観測する。一方、更新計画のように小さな集合と依存関係で表せる判断は、入力の組み合わせを機械的に探索できる。テスト例の追加に加え、概念上の不変条件と、詳細な計画処理の対応を明記したい。

TLA+ のモデル検査に成功しても、C++ のコードが自動的に証明されるわけではない。モデルの範囲、入力の境界、実装との対応、除外した障害を明示する必要がある。

## 決定

更新分の計画について、結果を宣言する [RefreshContract.tla](../contracts/formal/RefreshContract.tla) と、処理を段階化した [RefreshPlan.tla](../contracts/formal/RefreshPlan.tla) を用意する。詳細モデルから抽象契約への refinement mapping を定義する。

| 性質 | 問う内容 |
| --- | --- |
| 型・集合の範囲 | 計画が指定したファイルの有限集合の範囲で動くか |
| 宣言した結果との一致 | 消去／索引化の最終集合が契約の式に一致するか |
| 共有依存の保持 | 保持するソースに必要な依存を、余分な掃除で消さないか |
| 変更対象の包含 | 必要な変更・依存元を消去対象に含むか |
| 索引化対象の完全性 | 現在のソースのうち、消去または未索引のものを落とさないか |
| 抽象契約への対応 | 内部の段階を隠した動作が抽象契約に従うか |

基準の探索範囲は 3 ファイルで、include／import を別関係として扱う。両関係を持つ制限付き構成と、一種類の全ての非自己辺構成を別設定で検査する。モデルの定数・制約・実際の状態数はモデル設定と実行レポートを正本とする。

共有依存を誤って消す変異モデルが失敗することも確認し、単に実行できた・常に真の条件を見たという検証を避ける。TLC の版と取得物の検証情報を固定する。

## 実装との対応

モデルの入力集合を `RefreshPlan::forUpdatedFiles` の入力へ、最終集合を `filesToClear`／`filesToIndex` へ対応させる。C++ 側の有限列挙・性質試験と、実際のストレージを通る既存試験でその境界を検査する。[RefreshPlan.h](../../src/lib/project/RefreshPlan.h)

これは C++ からモデルへの自動変換や、C++ の全実行に対する機械証明ではない。モデルとコードの対応表は人が保守する。計画式・依存取得・入力分類を変更するときは、関連するモデル・契約・試験も再確認する。

## 検証しないもの

| 対象外 | 別に必要な確認 |
| --- | --- |
| 任意数のファイルへの一般的な定理 | 証明、または明示的な追加の推論 |
| mtime・ファイル内容・パス正規化 | ファイルシステム境界の試験 |
| 不完全ファイルの再試行を含む全モード | 対応する追加モデルと実装試験 |
| C++／Python の意味解析自体 | 言語ごとの適合例、実アプリ比較 |
| DB の消去・公開・復旧 | 障害モデルと障害注入 |
| ワーカー、共有メモリー、取消、進行性 | 並行処理の状態機械と公平性の前提 |
| GUI・検索順位 | 問い合わせ・操作の観測試験 |

特に、現行の DB 公開は旧ファイルを削除した後に rename する。今回のモデルは DB 公開を含まず、原子性やクラッシュ耐性の証拠には使えない。

## 代替案と影響

仕様を文章だけにすると組み合わせの検査ができない。実装のコピーを別言語で走らせるだけでは同じ誤りを重複し得る。最初から全アプリを形式化すると、抽象化の妥当性を確認しにくい。このため、今回は小さな結果契約と詳細モデルを対応させ、実装試験と併用する。

モデル検査が成功した際は「この境界・この定数・この性質について反例が見つからなかった」と報告する。探索範囲外まで「ソフト全体の同等性を証明した」と言い換えない。
