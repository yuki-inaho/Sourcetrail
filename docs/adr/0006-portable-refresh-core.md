# ADR-0006: 可搬な値処理と既存アダプターを分離する

- 状態: 採用
- 日付: 2026-10-30
- 関連判断: [ADR-0002](0002-pure-refresh-planning.md) の境界を具体化し、[ADR-0004](0004-language-capabilities.md) の段階的な分離方針に従う
- 関連契約: `REFRESH-001`, `REFRESH-002`, `COMMAND-001`, `PORTABILITY-001`, `PROCESS-001`, `VERIFICATION-001`
- 確認対象: [更新計画コア](../../src/lib_core/RefreshPlanner.h)、[従来の更新計画アダプター](../../src/lib/project/RefreshPlan.cpp)、[コマンド変数展開コア](../../src/lib_core/IndexerCommandTemplate.h)

## 背景

更新計画は集合演算として分離されていたが、公開型が `FilePath` と依存問い合わせコールバックを含んでいた。計画を再利用する側もアプリケーションのパス型を取り込む必要があり、別言語へ移すときの入力境界が曖昧だった。実際の計算に必要なのはファイルシステムへのアクセスではなく、識別子の集合と依存問い合わせの結果である。

外部索引器のコマンドでも、文字列中の変数展開と、Qt の保存形式、プロジェクト設定、ファイルパス、言語ごとの引数構築が近接していた。Python と Custom の Source Group には、選ばれたソースごとのコマンド生成に共通処理がある。[SourceGroupPythonEmpty.cpp](../../src/lib_python/project/SourceGroupPythonEmpty.cpp)、[SourceGroupCustomCommand.cpp](../../src/lib/project/SourceGroupCustomCommand.cpp)

ここで新しい抽象クラス群や公開プラグイン ABI を導入すると、既存の振る舞いと無関係な設計判断が増える。まず、既に使っている純粋な値処理を小さく切り出し、既存の呼び出し経路へ戻す。

## 決定: 標準ライブラリーだけのコア

[src/lib_core](../../src/lib_core/) を、Qt、Boost、SQLite、`FilePath`、OS のプロセス API を参照しない値処理の境界とする。アプリケーションを使わない小さな試験から同じ本番コードをコンパイルできる構成とする。アプリケーションの内部 API は、既存のアダプターを通して保つ。

| 処理 | コアが受け取るもの | コアが返すもの | アダプターに残す責務 |
| --- | --- | --- | --- |
| 更新対象の選択 | 全ソース、変更ファイル、変更の依存元の識別子集合 | 当初の消去集合、保持するソース集合 | ファイル列挙、変更判定、依存関係の取得 |
| 更新計画の完成 | 選択結果、未変更の索引済み集合、両側の依存先集合 | 消去集合、索引化集合 | 保存上の分類、実行、公開 |
| コマンド変数の展開 | コマンド／個々の引数、プロジェクト・DB・版・ソースの文字列 | 同じ境界のコマンド／引数列 | パス解決、設定取得、Qt の保存形式、子プロセス起動 |

外部コマンドの生成は [ExternalIndexerCommandBuilder](../../src/lib/data/indexer/ExternalIndexerCommandBuilder.h) にまとめる。言語側は `ExternalIndexerCommandSpec` に種別、実行ファイル、引数、並列可否を渡す。共通側の `createExternalIndexerCommands` が、対象ソースと索引化予定の積集合を既存の集合順に走査し、プロジェクト・DB・保存版を付けてコマンドを作る。Python の環境指定、verbose／shallow、Custom の利用者指定コマンドはそれぞれの Source Group に残す。

### 更新計画を二段階にする理由

`sourcetrail::core::prepareUpdatedRefresh` は、`allSourceFiles`、`changedFiles`、`referencingChangedFiles` から `RefreshSelection<Key>` を作る。値は `initialFilesToClear` と `staticSourceFiles` である。

`sourcetrail::core::finishUpdatedRefresh` は、全ソース、変更されていない索引済み集合、選択結果、保持側の依存先、当初の消去側の依存先から、`RefreshPlan<Key>` の `filesToClear` と `filesToIndex` を返す。`Key` は集合の順序付けで同一性を判定できる不透明な識別子であり、コアはパス文字列を読まず、パスを正規化しない。

二段階には同じ全ソース集合を渡し、依存結果は同じスナップショットから取得する。コアが新たにその一致をストレージへ問い合わせることはない。アダプターの前提と、値処理自体の決定性を分ける。

従来の [RefreshPlan](../../src/lib/project/RefreshPlan.h) は `FilePath` を使うアダプターとして残る。次の問い合わせ順序を保持する。

1. `referencing(changedFiles)` を読む。
2. コアで当初の消去集合と保持するソース集合を決める。
3. `referenced(staticSourceFiles)` を読む。
4. `referenced(initialFilesToClear)` を読む。
5. コアで最終の消去集合と索引化集合を決める。

二段階は、この既存の問い合わせ順を変えずに、コアをコールバックから切り離すための分割である。全依存グラフを前もってコピーする方式や、新たなファイル ID の割当方式は追加しない。include と import の推移閉包は既存ストレージが別々に計算した結果を使う。コアで閉包を取り直さない。

### コマンド展開で保つこと

`expandIndexerTemplate` と `expandIndexerArguments` は文字列型をパラメーターにし、現在の `std::wstring` と UTF-8 の `std::string` で同じ規則を使える。変数の展開は `PROJECT_FILE_PATH` → `DATABASE_FILE_PATH` → `DATABASE_VERSION` → `SOURCE_FILE_PATH` の順で行う。前の置換値に後の変数が含まれる場合は後の段階で展開し、同じ変数や既に処理した変数を再帰的に展開しない。引数を一つのシェル文字列へ結合しない。

保存するコマンドと引数は未展開のテンプレートであり、実行に使う値を取得した時に展開する。ワーカー別の DB パスへの変更も、その後の展開に反映される。この境界を変えると、単純な文字列比較が合っていても外部索引器が別の DB に書く可能性があるため、明示的な受入条件とする。[IndexerCommandCustom.cpp](../../src/lib/data/indexer/IndexerCommandCustom.cpp)

## SOLID・KISS・DRY をどう適用するか

| 原則 | 今回の具体的な変更 | 過度に一般化しない点 |
| --- | --- | --- |
| 単一責務 | 集合計算、文字列展開、入力取得、索引器起動を区別する | 更新の全工程を一つの新サービスへ集約しない |
| 拡張と置換 | 識別子と値を供給すれば同じ更新計算を使える。既存の `FilePath` 呼び出し口を保持する | 新しい言語を受け入れるだけの架空の実装を追加しない |
| 小さなインターフェース | コアには必要な集合と文字列だけを渡す | `Project`、`SourceGroup`、ストレージ全体を渡さない |
| 依存の方向 | コアはアプリケーションを参照せず、既存アダプターがコアを呼ぶ | 抽象クラスの数を増やすこと自体を目的にしない |
| KISS | 値と小さな関数で表し、既存の集合型・引数列を使う | 新しいプラグイン管理、IPC、独自のパス規則は作らない |
| DRY | 本番経路と単独試験が同じコアを使用し、共通のコマンド生成を共有する | 異なる言語の意味解析まで同じ処理へ押し込まない |

これらの原則への準拠を、クラス数や行数だけで判定しない。依存先が減ったか、同じ意味を別環境から検証できるか、既存の観測を保ったかで評価する。

## Rust などへの移行に渡す境界

更新計画の移植単位は、識別子の集合を入力し、消去と再索引化の集合を返す値処理である。C++ のオブジェクトレイアウトや `std::set` のメモリー表現を公開 ABI としない。別言語への移植では、同じ値に対する期待結果で検査する。

文字列展開も、文字列と引数の境界、置換順、未展開テンプレートの保存を契約として渡せる。OS 固有のプロセス作成と、Unicode の実際の受け渡しは、別途アダプターの実行試験を必要とする。

この分離だけでは、Rust のソース解析、Cargo 設定、trait／impl の意味、マクロ由来の位置は実装されない。Rust でコアを再実装することと、Rust を解析対象として追加することは別の作業である。[言語互換性と拡張点](../architecture/language-compatibility.md)

### 値の契約を別言語から確認する形式

検証用に `refresh-sets-v1` を定め、[C++ driver](../../tests/portability/refresh_driver.cpp) は本番の更新コアを呼び、[Rust reference](../../tests/portability/refresh_reference.rs) は標準ライブラリーの `BTreeSet` で同じ集合契約を実装する。これは製品の公開 ABI や IPC の採用ではなく、移植する単位を具体的に比較するための入出力形式である。

一行の入力は、順に次の六つの符号なし 64 bit 整数を十進数で表す。各 bit は不透明なファイル識別子を表す。

| 順序 | 入力集合 |
| --- | --- |
| 1 | 全ソース |
| 2 | 変更されていない索引済みファイル |
| 3 | 変更ファイル |
| 4 | 変更ファイルの依存元 |
| 5 | 保持するソースの依存先 |
| 6 | 当初の消去対象の依存先 |

出力は、当初の消去対象、保持するソース、最終消去対象、索引化対象の四つのマスクとする。依存の閉包を計算してこの入力を用意する側と、その結果を受け取るコアを区別する。実際のコアは `std::set<Key>` を受け取り、64 ファイルに制限されない。64 bit はこの検証用の表現の範囲である。

[refresh_vectors.json](../../tests/portability/refresh_vectors.json) の手書き期待と、三識別子の有向グラフ・入力集合の有限列挙を、[check_portability.py](../../script/verification/check_portability.py) が両実装へ渡す。独立した真偽値のオラクルとも比較し、二つの実装が同じ誤りを出して一致するだけでは合格にしない。共有依存の保護を意図的に省いた Rust の変異版も実行し、決めた反例で差が出ることを要求する。入力の bit 63 も明示例に含め、三識別子の列挙だけで型の範囲を見逃さない。

検証環境には Qt・Boost を入れない。依存がないと説明するだけでなく、独立した C++／Rust のビルドと実行で境界を確認する。成功した版、件数、出力、実行ファイルのハッシュは検証の証跡であり、他 OS や全ての Rust コンパイラーでの成功を暗黙に含めない。

```sh
pixi run -e portability --locked test-core
pixi run -e portability --locked verify-portability
```

前者は `src/lib_core` を独立して構成・ビルドし、更新計画とコマンド変数展開の試験を行う。後者はその試験に加えて、C++ と Rust の値単位の適合確認を行う。通常の `pixi run --locked verify` にも、アプリケーション試験、形式モデル、文書検査とともに組み込む。[pixi.toml](../../pixi.toml)

2026-10-30 の実行では、独立したコアの二つの CTest が成功し、GCC 12.4.0 の C++ 本番コアと Rust 1.85.1 の参照実装は、それぞれ手書き十例と有限列挙 32,768 例、合計 32,778 例で独立オラクルとの不一致がゼロだった。有限列挙は三識別子の自己辺を除く有向グラフ 64 通りと、全ソース・変更・未変更の各集合八通りの組合せであり、変更集合と未変更集合の重なりも含む。両実装の出力ハッシュは一致した。共有保護を省く変異版は `shared-and-private` と `protect-static-source` で不一致となり、必須の反例を検出した。[検証レポートと証跡](../reports/2026-10-30/005-portable-core-and-verification/report.md)

## 検証

更新計画では、アプリケーションをリンクしない整数識別子の試験と、既存の `FilePath` アダプターの有限入力試験を組み合わせる。コアを切り出した後も、TLA+ が記述する集合の契約は変えない。

外部コマンドでは、複数の変数、順序の影響、空値、未対応の変数、引数境界、DB の切り替え、未展開の保存形式を確認する。実アプリ全体では [ADR-0005](0005-toy-project-conformance.md) の C++／Python の同一入力を使い、変更前後の厳密な観測を比較する。実行した範囲と結果は [reports](../reports/README.md) に残す。

トイの基準実行では、可搬コアへの変更前から、C++ の削除更新で三つの所属関係が欠ける差を発見した。その保存層の修正は本 ADR の構造変更とは別の意図した変更として扱う。修正する観測差を明示し、残りの観測に説明のない差を作らない。[基準の差](../contracts/toy-problems.md#最初の基準実行で見つかった既存の差)、[消去の規則](../architecture/storage-and-query.md#注入消去キャッシュ)

実際の確認では、修正だけを加えた成功基準と、可搬コア・共通コマンド構築を含む変更後の実アプリを比較し、C++ 七段階と Python 七段階の全スナップショットが一致した。独立期待と、無変更／全体更新との八つの比較も成立した。確認したのはこの入力・能力・観測プロファイルの範囲であり、全入力への一般的な等価性ではない。[005: 変更前後の分離した検証](../reports/2026-10-30/005-portable-core-and-verification/report.md)

## 代替案と残る制約

アプリケーション全体を別言語で一度に書き換える案は、比較する責務が大き過ぎる。現行型をそのまま外部 ABI へ出す案は、パス・コンテナー・Qt の版に依存する。将来の全機能を表す汎用プラグイン層を先に作る案は、未実装の要求を固定してしまう。いずれも今回の値処理の分離には必要ない。

可搬性の改善は、コアをアプリケーションの依存から独立してコンパイルできる範囲で評価する。Sourcetrail 全体の Windows／macOS 対応、プロセスの終了状態の再設計、DB 公開の原子性、依存スナップショットの同期、mtime の検出方式、性能はこの判断の達成事項へ含めない。未達成の事項は [改善計画](../architecture/evolution-plan.md) で引き続き追跡する。
