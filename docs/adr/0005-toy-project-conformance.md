# ADR-0005: 人工的な小規模対象を独立した期待値と実索引結果で確認する

- 状態: 採用
- 日付: 2026-10-30
- 関連判断: [ADR-0001](0001-semantic-observations.md)、[ADR-0002](0002-pure-refresh-planning.md)、[ADR-0003](0003-bounded-formal-verification.md)、[ADR-0004](0004-language-capabilities.md)
- 関連契約: `GRAPH-001`, `NAME-001`, `RELATION-001`, `LOCATION-001`, `REFRESH-001`, `REFRESH-002`, `SOURCE-GROUP-001`, `STORAGE-002`, `VERIFICATION-001`
- 詳細仕様: [トイプロブレムの設計と確認方法](../contracts/toy-problems.md)

## 背景

実際の対象プロジェクトは、言語機能、外部依存、ビルド条件が重なり、索引の差がどの責務に由来するかを切り分けにくい。既存の試験は有用だが、試験関数の中で文字列として組み立てる入力だけでは、別のエージェントが入力・期待・設計理由を並べて読む作業が難しい。

また、変更前後の結果だけを比べると両方にある誤りを検出できず、期待した数個の記号だけを確認すると未指定の位置・曖昧性・定義状態の退行を見逃す。リファクタリング前の実行結果を保存しつつ、実装からコピーしていない小さな期待値が必要になる。

## 決定

人工的な C++ と Python の対象を [tests/toy_projects](../../tests/toy_projects/) にソースファイルとして保存する。各対象は一つの宣言した解析プロファイルを持ち、初期版、変更版、削除するファイル、期待する意味をコードと一緒にレビューできる構成とする。ユーザーの実プロジェクトやネットワーク依存を必要としない。

検証は次の三層に分ける。

| 層 | 判定すること | 判定の根拠 |
| --- | --- | --- |
| 独立した期待値 | 指定した名前・シグネチャ・有向関係・位置・ファイル状態が存在し、削除済み／旧名の記号が残らない | 人が小さな対象を読んで作る `expected.json` |
| 一回の実行内の同等性 | 無変更更新が初回と一致し、削除・編集後の更新が別ルートの全体索引化と一致する | `schema25-exact-v1` による全観測の比較 |
| 変更前後の同等性 | 固定した入力と設定に対し、変更後の各段階が変更前の各段階と一致する | 変更前に保存したスナップショットと入力・設定の識別情報 |

この三層は互いを代替しない。指定した期待値の成立は全観測の同等性ではなく、全観測の同等性もプログラムの正しさの完全な証明ではない。入力・期待値・プロファイルを変更した場合は、旧基準との単純な同等比較を続けず、変更理由と新しい受入条件を明記する。

## トイプロブレムの選び方

| 対象 | 最小限含める構造 | 既存構成から選んだ理由 |
| --- | --- | --- |
| `TOY-CXX-001` | 共有ヘッダー、名前空間、`int`／`double` の同名関数、両方を呼ぶ `entry`、複数翻訳単位、削除する呼び出し元 | 内部 Clang 解析、シグネチャを含む名前、include 依存と差分更新を一緒に観測できる |
| `TOY-PYTHON-001` | import、親子クラス、メソッド／関数の呼び出し、順序の異なる二つの Source Group、後続グループでの削除 | 外部索引器、import 関係、継承、部分消去不可グループから全体更新への切り替えを観測できる |

両言語で「定義を識別し、参照をたどり、変更後に古い対象が消える」という概念を確認する。一方、C++ のオーバーロードと Python の動的解決を同じ保存名へ縮めない。言語間で SQLite グラフを完全一致させる判定は採用しない。追加する Rust 等の対象には、対応する共通概念と、その言語固有の期待をそれぞれ定義する。

## 実行と証跡

実アプリの CLI を使用し、初回全体更新、無変更更新、削除、削除後の独立した全体更新、編集、編集後の独立した全体更新、編集後の無変更更新を記録する。日本語と空白を含む異なる作業ルートに入力を配置し、宣言したルートだけを正規化する。入力ソースの文字列やシグネチャを都合よく消して比較しない。

各段階でコマンドの終了状態だけでなく、DB の構造、必要な意味、診断、`indexed`／`complete` を調べる。外部索引器の失敗が空の成功へ変わらないよう、実行不能、観測欠損、比較条件の不一致を失敗とする。

リファクタリングに先立って基準を実行し、その後に変更後の実アプリを再ビルドして同じ対象を実行する。レポートには比較の基準コミット、入力の版、実行したコマンド、各段階の結果、比較器の版、未確認事項を残す。実行履歴の入口は [reports](../reports/README.md) とする。

最初の適用結果は、[004: 設計と変更前の基準観測](../reports/2026-10-30/004-toy-project-design-and-baseline/report.md) と [005: 可搬コアへの変更と検証](../reports/2026-10-30/005-portable-core-and-verification/report.md) に残す。元実装で見つかった C++ の所属関係の欠落、修正だけを加えた実行、構造変更後の十四段階の一致を区別して追跡する。

## 代替案

| 案 | 採用しない理由 |
| --- | --- |
| 自動生成した DB だけを試験する | 実際の設定読込、解析器起動、索引更新を通らない |
| 既存の出力をそのまま正解ファイルにする | 旧実装の誤りを独立して発見する基準にならない |
| 名前・辺の件数だけを比較する | 同数の別記号、逆向きの関係、誤った位置を見逃す |
| 一つの巨大な合成プロジェクトを作る | 差分の責任範囲が広がり、設計理由と最小再現条件が追いにくい |
| 全言語に同じ完全グラフを要求する | 言語の名前体系、解決能力、位置表現の違いを隠す |

## 影響と未達成事項

入力と期待値が別ファイルで読めるため、コードの移動や別言語への再実装でも同じ受入条件を再利用できる。共通の実行・比較処理を一箇所に置き、言語別には対象の構成と期待値だけを持たせる。

この有限の例は、全構文、全 OS、巨大プロジェクト、性能、GUI 操作、検索順位、クラッシュ復旧を保証しない。TLA+ の有限更新モデルと C++ の集合演算試験も継続し、トイプロブレムで形式検証を置き換えない。対象の新規追加は、未確認事項を一つずつ受入条件へ変える作業として扱う。
